# Downstream-impact audit: everything that cites a distance-resolved number built on `vessel_profile.vessel_mask_from_density`

**Purpose.** A pure citation/dependency audit — no new computation, no simulation runs, no file modifications. Maps every place in this repository that quotes, tabulates or narratively depends on a **distance-from-vessel-resolved** number whose vessel mask is `tmesim/validation/vessel_profile.py::vessel_mask_from_density` (a percentile threshold on `vascular_density`) followed by `distance_from_vessel_um` / `distance_profile`. The goal is to make the blast radius of a fix to that mask fully known before anyone touches it.

**Method.** Grep across `results/*.md`, `docs/*.md`, `README.md`, `app/`, and Python source for: `vessel_profile`, `vessel_mask_from_density`, `distance_from_vessel_um`, `distance_profile`, `penetration_length`, `d_half`/`d½`, and the headline numeric outputs (e.g. `31.8`, `276.8`, `786`, `43`). Every hit was read in context and classified.

---

## 0. A finding that changes how to read this whole audit — read first

The premise handed into this audit ("the percentile-threshold vessel mask gives a distance ~3× larger than the true cell-position measurement") does not literally match what the two documents that make this comparison currently say, and the discrepancy is itself the most important finding here.

**Three independent implementations of "distance from a vessel" exist in this repo, and they currently disagree with each other in ways the docs do not consistently reflect:**

1. **`vessel_profile.vessel_mask_from_density`** (`tmesim/validation/vessel_profile.py:173`) — the function actually in question. It thresholds `vascular_density` at the 95th tissue percentile, **but has an explicit fallback**: "When the threshold comes out non-positive we ... fall back to `vasc > 0`" (lines 190-198), added per `results/vessel_promotion.md` for the current default **discrete** vascular source (`_DEFAULT_VASCULAR_MODE = "discrete"`, `tmesim/reconstruct/real_fields.py:162`), which is exactly zero over ~97.5% of tissue so the raw percentile is degenerate. **With this fallback in place, `vessel_profile.md`'s own primary-arm distance map (median 43 µm, p95 102 µm, max 786 µm) is within a few percent of the independently cell-position-measured 44.2 µm median in `vascular_validation.md` §3.4.** i.e., as currently patched, this specific function is **not** obviously biased 3× high — the fallback appears to have already substantially fixed the pathological case for the discrete-source default.
2. **`vascular_validation.field_based_distance`** (`tmesim/validation/vascular_validation.py:499-530`) — a **separate, parallel reimplementation** of the identical percentile-threshold + `distance_transform_edt` logic, explicitly documented as mirroring `vessel_profile.vessel_mask_from_density` (line 503-504 docstring), but **it does not carry the sparse-source fallback**. Under the current discrete-mode default, `np.percentile(vasc[tissue], 95)` is 0.0 (≥97.5% of the field is exactly zero), so `mask = vasc >= 0.0` selects essentially the **entire tissue** as "vessel," and every distance collapses toward 0. This is exactly what the current `results/vascular_validation.md` (regenerated most recently of the files inspected, `Jul 29 00:36`) reports: **"gives a median tumour-to-'vessel' distance of 0 µm (p90 0 µm), 0.0× larger than the 44 µm"** (§5, "The opposing bias"). That "0.0×" is very likely this second, un-patched function silently returning a degenerate answer under the discrete-source default it was never updated for — not a real measurement of the mask's bias.
3. **`oxygen_proxy.oxygen_from_vessel_distance`** (`tmesim/physics/oxygen_proxy.py:421`, `cKDTree` on cell positions) — a **third, independent** implementation used by the `vessel_distance` oxygen-surrogate route (`reconstruct/real_pipeline.py`, cited in `results/kill_calibration.md:245`, `results/cell_state_impact.md`, `results/oxygen_demotion.md`). It does not use a percentile-threshold field mask at all, so it is **not at risk** from a fix to `vessel_mask_from_density`.

**`results/vessel_network_impact.md` (generated `Jul 28 00:59`, before `vascular_validation.md`'s latest regeneration) cites the comparison as "the two definitions to disagree by 3.0×"** — this is presumably where the "~3×" figure came from, but it is now **stale relative to the currently-published `vascular_validation.md`**, which shows a 0.0× (degenerate) ratio from what looks like the same underlying bug interacting with the discrete-mode switch. Neither `results/SESSION_AUDIT.md` nor `results/reconstruction_validation_roadmap.md` currently tracks this specific cross-document inconsistency (see §4 below).

**Practical upshot for planning the fix:** the actual bug to fix may need to land in **two places**, not one — `vessel_profile.vessel_mask_from_density` (already partially patched, may still be biased for reasons unrelated to the degenerate-threshold case, e.g. still selecting hotspots-not-vessels under the KDE mode) and `vascular_validation.field_based_distance` (not patched at all, and currently produces a number that materially misstates the comparison it exists to make). Whoever does the fix should re-run `vascular_validation` before trusting its own "0 µm / 0.0×" framing of the problem.

## 1. What actually calls the vessel-mask / distance functions

`vessel_mask_from_density`, `distance_from_vessel_um`, and `distance_profile` are all defined once in `tmesim/validation/vessel_profile.py` and imported elsewhere — so a fix there propagates to every caller below (with `vascular_validation.py`'s parallel reimplementation, §0, being the one exception that would need its own patch).

| caller (Python) | imports from `vessel_profile` | drives which results file(s) |
|---|---|---|
| `tmesim/validation/vessel_profile.py` (itself) | defines them | `results/vessel_profile.md`, `results/vessel_profile.png` |
| `tmesim/validation/delivery_metrics.py` | `vessel_mask_from_density`, `distance_from_vessel_um`, `distance_profile` | `results/delivery_metrics.md`; feeds `app/server/jobs.py` (live API) |
| `tmesim/validation/heldout_patient.py` (via `delivery_metrics as DM`) | `DM.vessel_mask_from_density`, `DM.distance_from_vessel_um` | `results/heldout_patient.md` |
| `tmesim/validation/vessel_network_impact.py` | `vessel_mask_from_density`, `distance_from_vessel_um`, `distance_profile` | `results/vessel_network_impact.md` (as the "legacy axis" comparator) |
| `experiments/dose_schedule.py` | all three | `results/dose_schedule.md`, `.png` |
| `experiments/combination.py` | all three | `results/combination.md`, `.png` |
| `experiments/regimen.py` | all three | `results/regimen.md` |

Separately, `app/server/jobs.py` and `app/server/report.py` expose `delivery_metrics`'s fitted length as the **live API field** `penetration_length_um` (distinct from the analytic `penetration_length_analytic_um` — see §3, Not-at-risk list). This is the single highest-exposure surface: every simulation run through the app UI/API returns this number to a user, not just a static markdown file.

## 3. Cross-reference against `SESSION_AUDIT.md` and `reconstruction_validation_roadmap.md`

**`results/SESSION_AUDIT.md`**
- §3 item 3 marks "discrete vessel network" **CLOSED**, and specifically calls out that `penetration_length_L` spread moved 1.07× → 6.91× as a resolved finding — but this closure is about the **KDE-vs-discrete vascular-source** question, not about the percentile-threshold-vs-cell-position discrepancy this audit is scoped to. It does **not** mention `vascular_validation.md`'s "0 µm" / "3.0×" number at all.
- §3 item 7 ("ranking robustness") is marked "STILL OPEN in spirit" for unrelated reasons (a different configuration).
- **Nothing in `SESSION_AUDIT.md` currently flags the mask-vs-cell-position distance discrepancy as open, provisional, or in need of re-verification.** This specific issue is untracked there.

**`results/reconstruction_validation_roadmap.md`**
- Rows 4-7 (MVD, intervessel spacing, median tumour→vessel distance, heterogeneity) are all about the **cell-based** measurement vs. published literature — i.e., they use the "ground truth" comparator column in the NOT-at-risk table above, not the percentile-mask output. They are marked FAILS relative to literature, but that is an absolute-calibration finding, unrelated to internal mask-vs-cell-position consistency.
- The roadmap's own methodological conclusion (line 34) — "every quantity here that is a point-pattern statistic derived from cell positions ... is fragile"; "the one quantity that is a stereological identity requiring no cell-type call at all ... is the most robust" — implicitly supports `vascular_validation.md`'s recommendation to move the vessel mask to cell-derived clustering, but again **does not reference the field-based/percentile-mask distance number or its internal inconsistency.**
- **Neither audit document currently tracks this citation-consistency issue.** It exists only inside `vascular_validation.md` §5/§7.2 and `vessel_network_impact.md` §3, and those two now disagree with each other on the magnitude (0.0× vs 3.0×) without either flagging the other.

## 4. Ranked risk list — what to check first once the fix lands

Ordered by (a) how directly the number is built from `vessel_mask_from_density`, and (b) how many other places cite or re-derive it (prominence).

1. **`results/vessel_profile.md`** — ground zero; every table changes. Regenerate first; everything else keys off it.
2. **`results/delivery_metrics.md`** (`penetration_length_L` / `penetration_length_fit`) — explicitly reuses `vessel_profile`'s functions "so the two reports cannot drift apart"; its 6.91× discrimination verdict and "NOT converged (16% grid drift)" caveat are exactly the kind of claim that could flip.
3. **Live API/app surface** (`app/server/jobs.py`, `report.py`, `protocol_wire.py`, `tmesim/protocol/executor.py`) — the `penetration_length_um` field returned to every simulation run. Highest real-world exposure of any item on this list, even though it's not a markdown "claim." Verify the naming collision with `penetration_length_analytic_um` doesn't cause the wrong field to be trusted/distrusted.
4. **`results/heldout_patient.md`** — per-drug, per-section `penetration_length_um`/`_source_null_um` columns; a held-out-section comparison, so any shift changes a cross-section generalization claim, not just a single-section number.
5. **`results/vessel_network_impact.md`** §3 — contains the *exact* "3.0×" claim this audit was framed around, and it is now the most likely single number to be cited by name once someone goes looking ("the two definitions ... disagree by 3.0×"). It should be the first thing re-verified against a freshly regenerated `vascular_validation.md`, since it currently disagrees with vascular_validation.md's own live text (§0).
6. **`results/vascular_validation.md`** §5/§7.2 — ironically both the *source* of the "percentile mask is biased" narrative and, right now, a document whose own supporting number for that narrative looks broken (degenerate 0 µm/0.0×, likely from its un-patched parallel `field_based_distance` implementation under discrete-mode). Needs its own fix (add the sparse-source fallback to `vascular_validation.field_based_distance`, or import `vessel_profile.vessel_mask_from_density` directly) — not just a re-run — before its number can be trusted again.
7. **`results/vessel_promotion.md`** — not itself "at risk" in the sense of needing correction (it's already a record of how the metric moves across mask/source changes), but it is the most useful **reference** for predicting what a further mask fix will do, and should be consulted while making the fix, not just checked afterward.
8. **`results/dose_schedule.md`, `results/combination.md`** — each independently rebuilds distance-binned profiles via `experiments/*.py` importing the same three functions; both have quoted numeric tables (43/85/786 µm geometry stats; per-drug half-distances) that would need regeneration.
9. **`results/dimensionality.md`** — doubly-derived (a 3-D correction on top of `delivery_metrics.md`'s already-DR `L`); must be regenerated *after* items 1-2, not independently, or it will combine a stale base number with a correction computed for the old base.
10. **`results/kill_calibration.md`** — cites the 786 µm max-distance figure and a narrative point ("our gradient is too steep, plausible since dose_schedule.md shows...") that depends on the shape of the current (possibly biased) profile; low numeric exposure, but the qualitative argument in §3 (item (i) of the three possible readings) could weaken or strengthen depending on which way the fix moves the gradient.
11. **`results/regimen.md`** — caveat-only citation (item 13), no specific number; update the cross-reference wording only.
12. **`docs/architecture.md:511-513`** — already-known-stale (superseded twice already, unrelated to this specific fix); cheap to fix in the same pass but not urgent on its own.
13. **`README.md`, `docs/DATA_INVENTORY.md`, `docs/REPRODUCE.md`** — purely descriptive/navigational; no numeric risk, no action needed beyond leaving links intact.

**Not at risk, confirmed by direct code inspection (no action needed):** `results/patient_report_xenium.md`, `results/patient_report_visium.md`, `results/breast_cancer_flagship.md` (analytic `penetration_length_um`, no mask); `app/server`'s `penetration_length_analytic_um` field; the `vessel_distance` oxygen-surrogate route (`kill_calibration.md`, `cell_state_impact.md`, `oxygen_demotion.md` — independent `cKDTree` implementation); `results/glioma_regional_pk.md` (self-declared out of scope); `results/vessel_geometry_fix.md` (different module/quantity); `results/vascular_validation.md`'s own cell-based MVD/spacing/heterogeneity numbers (§1-§4, computed from cell positions, not the percentile mask — these are the "ground truth" side of the comparison, not a consumer of the biased function).

## 5. One process recommendation (observation, not a request to act)

Given §0, the fix likely has two parts, not one: (a) whatever change is made to `vessel_profile.vessel_mask_from_density` itself, and (b) syncing or removing the parallel, unpatched reimplementation in `vascular_validation.field_based_distance` — otherwise the two documents that are supposed to cross-check each other (`vascular_validation.md` and `vessel_network_impact.md`) will keep drifting out of sync the way they already have. Whoever does the fix should regenerate `vascular_validation.md` and `vessel_network_impact.md` together, in the same pass, and reconcile the "0.0×" vs "3.0×" figures explicitly rather than letting a third value silently replace both.

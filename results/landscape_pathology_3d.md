# Landscape survey: digital pathology and 3D histology tooling, as ingestion sources for tme-sim

**Purpose.** tme-sim reconstructs a tumour microenvironment and runs drug-transport physics on it. It is downstream of measurement — it does not segment or classify tissue itself. Today it consumes 10x Xenium/Visium spatial transcriptomics on single 2D sections. This document surveys the software that already turns pathology slides (and cleared/light-sheet volumes) into quantified, structured tumour information, documents exactly what each tool *outputs*, and makes a costed recommendation for what to build an ingester against next.

**Method note.** This is a research survey compiled by parallel web/PubMed research passes with a subsequent adversarial verification pass on the highest-stakes claims (the CODA vasculature claim, the QuPath/VALIS export claims, and — most heavily — the "is there a public 3D human GBM vascular network" question, which was independently re-searched by a second agent across Zenodo, BioImage Archive, IDR, Brain Image Library, Human Organ Atlas, EBRAINS, and Synapse before being marked CONFIRMED as a negative result). Every claim below is cited. Anything not confirmed by a primary or strong secondary source is explicitly marked **UNVERIFIED**.

## Part 1 — 2D whole-slide pathology quantification tools

### QuPath (open source) — the most practical ingestion target

- **License**: GPLv3, fully open source, free. Bankhead P, et al. "QuPath: Open source software for digital pathology image analysis." *Scientific Reports* 7, 16878 (2017). DOI: [10.1038/s41598-017-17204-5](https://doi.org/10.1038/s41598-017-17204-5).
- **What it quantifies**: nucleus/cell detection, cell classification (including multi-class/composite classifiers), pixel-classifier-based tissue region classification (e.g. tumour/stroma), per-cell IHC staining measurements (e.g. mean DAB optical density), TMA core analysis. [Cell detection tutorial](https://qupath.readthedocs.io/en/stable/docs/tutorials/cell_detection.html), [cell classification tutorial](https://qupath.readthedocs.io/en/0.4/docs/tutorials/cell_classification.html).
- **Export formats — confirmed by direct fetch of official docs**:
  - **GeoJSON** is the documented "preferred method" for object export. GUI: `File → Object data → Export as GeoJSON`. Script: `exportObjectsToGeoJson(objects, path, "FEATURE_COLLECTION")`. Works on detections (cells) as well as annotations by swapping `getDetectionObjects()` for `getAnnotationObjects()`. The `FeatureCollection` carries per-object `classification` and `measurements` properties; coordinates are in pixel units, origin top-left. Known quirk: ellipses become polygons on export. Source: [qupath.readthedocs.io/.../exporting_annotations.html](https://qupath.readthedocs.io/en/stable/docs/advanced/exporting_annotations.html) (verified by direct fetch).
  - Also supports **WKT** and **WKB** geometry export (via JTS `WKTWriter`/`WKBWriter`), and **ImageJ ROI zip** export. Source: same docs page.
  - **.qpdata**: the per-image project save file. This is a **raw Java-serialized object**, and QuPath's own FAQ states reading/writing it outside Java is "likely to be prohibitively difficult/impossible." **Not a viable ingestion format.** Source: [qupath.readthedocs.io/.../faqs.html](https://qupath.readthedocs.io/en/stable/docs/reference/faqs.html).
  - **Measurement TSV/CSV export**: `Measure → Export measurements`, per-object (cells/detections/annotations/TMA cores), user-selectable columns, across one or many images in a project. Source: [qupath.readthedocs.io/.../exporting_measurements.html](https://qupath.readthedocs.io/en/stable/docs/tutorials/exporting_measurements.html).
  - **Per-cell centroid table via scripting**: QuPath's own GitHub wiki publishes a ready-made Groovy script that emits a literal `class\ty\tx` table from `getDetectionObjects()` centroids — i.e. QuPath does not include x/y in the default measurement export, but a one-line official script produces exactly the "cell ID + coordinates + class" table format tme-sim would want. Source: [github.com/qupath/qupath/wiki/Scripting-examples](https://github.com/qupath/qupath/wiki/Scripting-examples).
  - No single formal schema document exists beyond these pages; QuPath's docs explicitly point users to the GeoJSON spec (RFC 7946) itself plus QuPath's own property conventions.
- **Per-cell vs aggregate**: confirmed per-object — GeoJSON carries full per-cell polygon + classification + measurements; the scripting route gives explicit per-cell x/y.
- **Public example exports to test an ingester against**: real, downloadable today —
  - [kbestak/QuPath_Annotation_to_Quantification_file](https://github.com/kbestak/QuPath_Annotation_to_Quantification_file) (GitHub)
  - [choosehappy/QuPathGeoJSONImportExport](https://github.com/choosehappy/QuPathGeoJSONImportExport) (GitHub)
  - MuSpAn docs bundle a sample `qupath_example_data.geojson` exported from real QuPath cell segmentation (exact download URL not surfaced in the fetched page, but it is described as a genuine QuPath GeoJSON export with per-cell measurements including nucleus area/circularity and multiplex stain intensities — [docs.muspan.co.uk](https://docs.muspan.co.uk/v1.1.0/_collections/importing_data/Importing%20data%20from%20QuPath.html), verified by direct fetch)
  - [cdQuPath](https://jianhong.github.io/cdQuPath/articles/cdQuPath.html) R package ships an `ExportCellDetectionMeasurement.groovy` script for generating GeoJSON cell-detection exports.
- **2D vs 3D**: primarily 2D. Bio-Formats backend can load z-stacks, but support is described in QuPath's own wiki and on the image.sc forum as partial/fragile — OpenSlide, a common backend, "can only return 2D RGB images... even if the original data was a z-stack." Serial-section registration is possible only via the external Fiji/BigDataViewer **Warpy** plugin, not natively. Source: [qupath wiki, supported formats](https://github.com/qupath/qupath/wiki/Supported-image-formats).

**Bottom line**: QuPath is the only tool surveyed with a genuinely public, documented, scriptable, and testable export pipeline. It is the clear #1 ingestion target.

## Part 2 — CODA: 3D reconstruction from serial H&E (Johns Hopkins, Kiemen et al.)

This is the centrepiece finding of the survey, verified directly against the primary paper.

- **Primary paper**: Kiemen AL, et al. "CODA: quantitative 3D reconstruction of large tissues at cellular resolution." *Nature Methods* 19(11):1490–1499 (24 Oct 2022). DOI: [10.1038/s41592-022-01650-9](https://doi.org/10.1038/s41592-022-01650-9). PMID: [36280719](https://pubmed.ncbi.nlm.nih.gov/36280719/). Full text (open): [PMC10500590](https://pmc.ncbi.nlm.nih.gov/articles/PMC10500590/) — verified by direct fetch.
- **Sections / z-spacing (confirmed by direct fetch of full text)**: 14 human FFPE pancreas specimens; sample P0 = 101 serial sections at **4 µm** thickness used only for pipeline validation. Main analysis set (P1–P13): **4,114 H&E sections total**, physically cut every 4 µm but only **every third section stained and used**, giving an **effective z-spacing of 12 µm**. They validate that skipping up to 3 axial planes (~12 µm) retains >95% pixel correlation / 96% cell-count accuracy, and show degradation trends out to 96 µm spacing. Lateral (xy) resolution: ~0.5 µm/px at scan (20x, Hamamatsu NanoZoomer), segmented at 2 µm/px.
- **Registration**: two-stage — (1) global rigid Radon-transform-based rotation/translation registration of all sections to a central reference, with a fallback to skip badly-torn/folded sections; (2) local elastic registration via tiled cross-correlation interpolated into a smoothed displacement field. Benchmarked against 7 other registration methods on a public 260-image mouse-prostate dataset; CODA had the lowest accumulated registration error across long stacks.
- **Vasculature claim — precisely characterized (this matters, and is more modest than the task brief implied)**: CODA labels blood vessels as **one voxel-wise semantic segmentation class** (via a per-sample-trained DeepLabv3+/ResNet50 model), rendered in 3D purely via MATLAB `isosurface`/`patch`. **Confirmed directly from the full text: there is no branch-point detection, no vessel skeleton, no radius/lumen modelling, and no connectivity graph anywhere in the paper.** Vessels are used qualitatively (e.g. tracing venous tumour invasion by eye against the segmented blob), not as a transport-ready network. **Note**: on direct fetch of the full text, the nine explicitly-named segmentation classes for the main pancreas model are normal ductal epithelium, precursor lesions, PDAC, smooth muscle, acini, fat, collagen, islets of Langerhans, and lymph nodes (plus nerves in a secondary model) — blood vessels appear in figures/3D renderings but were **not** confirmed as one of the nine formally-named classes in the text passages retrieved; treat "vasculature as a segmented class" as supported by the figures/prose ("surrounding acinar lobules, islets of Langerhans, fat, and blood vessels" is a direct quote) but the exact class list is **UNVERIFIED beyond nine core + vessels-in-renderings**.
- **Outputs / file formats**: a 3D multi-labelled voxel matrix (MATLAB, resampled to isotropic 12×12×12 µm/voxel) plus a parallel 3D cell-centroid coordinate matrix; visualizations via MATLAB `patch`/`isosurface`/`scatter3`. No confirmed mesh export format (STL/OBJ/PLY) in the base pipeline — a 2024 follow-up paper on 3D-printing CODA reconstructions (Kiemen et al., *Advanced Materials Technologies*, DOI [10.1002/admt.202301837](https://advanced.onlinelibrary.wiley.com/doi/abs/10.1002/admt.202301837)) implies a mesh-export step exists for physical printing, but the exact format is **UNVERIFIED**.
- **Software availability**: GitHub [ashleylk/CODA](https://github.com/ashleylk/CODA) (no explicit license on the repo itself — `license: null`), plus an archived, versioned, **CC-BY-4.0-licensed** release on Zenodo: [zenodo.org/records/11130691](https://zenodo.org/records/11130691). A step-by-step protocols.io tutorial series exists under NIH HuBMAP ("CODA: 3D tissue reconstruction pipeline | HuBMAP | JHU-TMC," [protocols.io](https://www.protocols.io/view/coda-3d-tissue-reconstruction-pipeline-hubmap-jhu-db8z2rx6.html)), with a Part 1 titled "setting up environment and preparing sample dataset" implying a bundled demo dataset — this could not be independently confirmed (protocols.io blocked automated fetch with HTTP 403), so treat the demo-dataset claim as **UNVERIFIED but plausible**.
- **Data availability of the actual paper's reconstructions**: verbatim from the paper — *"Data is available upon request from the corresponding author."* **Not openly downloadable.**
- **Tissues applied to**: human pancreas (primary), human scalp/skin, murine lung, murine liver.
- **Brain/GBM application — negative finding**: extensive PubMed and web search (both the original agent and confirmed by the adversarial verification pass) found **no publication applying CODA, or a named derivative, to brain tissue or glioblastoma**, as of this survey (2026). All follow-up CODA work located (3D-printed pancreatic microanatomy 2024; pancreatic-precancer immune remodeling, *Cell Press Blue* 2026, DOI [10.1016/j.cpblue.2026.100008](https://doi.org/10.1016/j.cpblue.2026.100008)) remains pancreas-only. **Stated plainly: no evidence CODA has been applied to brain or GBM tissue.**
- **Key limitation for reuse**: a fresh DeepLab segmentation model must be manually trained per tissue sample (~50 annotated examples/class on ≥7 sections, ~1 day of work), because CODA has no generalized pretrained tissue-type model — this is a real barrier to a lab "just handing over" a CODA output without significant per-case ML effort.

PASTE2/STalign are the right tools only if the workflow is ST spot data rather than raw stained WSIs — which is notable, since tme-sim's *existing* Xenium/Visium ingestion already sits in exactly that spot-data regime, making PASTE2/STalign a plausible near-term "stack 2D sections into a pseudo-3D volume" option using data tme-sim already knows how to read.

## Part 4 — Whole-slide image file formats: what a lab would actually hand over

- **No convergence at the proprietary layer.** Main formats in real use: **Aperio SVS** (Leica), **Hamamatsu NDPI**, **Leica SCN**, **3DHistech MRXS**, **Philips iSyntax/TIFF**, **Zeiss CZI**. A 2024 ESDIP pathologist survey (predominantly European) found simultaneous multi-format use: TIFF/TIF 69.6%, SVS 58.5%, MRXS 40%, NDPI 30.4%, DICOM "routine use" only 11% ([Laboratory Investigation, S0023-6837(24)01881-6](https://www.laboratoryinvestigation.org/article/S0023-6837(24)01881-6/fulltext) — cited secondhand via search excerpt, direct fetch was paywalled/403, flagged **UNVERIFIED at primary-source level** for exact percentages).
- **Philips iSyntax is the famously hard case**: closed spec, no open-source reader exists; OpenSlide and Bio-Formats both explicitly do not support it; the only tools that touch it (isyntax2raw, OpenPhi, PMC8570784) wrap the proprietary, license-gated Philips SDK.
- **OME-TIFF / OME-NGFF (OME-Zarr)**: genuine open interoperability formats, but function as a **conversion/research-tooling target**, not something scanners natively output or labs hand over. `bioformats2raw`/`raw2ometiff` can convert proprietary formats (including MRXS) into this space. Write-capable OME-Zarr tooling in production pathology pipelines is still immature.
- **DICOM WSI (Supplement 145)** has the most institutional/regulatory momentum but is **not yet what a lab hands over today**: only ~11% "routine use" per the ESDIP survey above; the **first and (as of this survey) only FDA-cleared scanner with native DICOM output is Leica's Aperio GT 450 DX** (FDA 510(k) K232202, April 2024, [Leica press release](https://www.leicabiosystems.com/us/news/leica-biosystems-receives-fda-510k-clearance-for-aperio-gt-450-dx-digital-pathology/), [FDA record](https://510k.innolitics.com/device/K232202)). DICOM WSI is real and growing on the *archival/repository* side — the NCI **Imaging Data Commons** stores all pathology collections natively in DICOM and converts submissions on ingest ([RadioGraphics, NCI IDC](https://pubs.rsna.org/doi/full/10.1148/rg.230180); [Slim viewer, Nat Comms](https://www.nature.com/articles/s41467-023-37224-2)) — but no named hospital system was found running DICOM WSI as its primary clinical output format today.
- **What tme-sim would most likely actually receive from an academic cancer research lab**: **Aperio SVS**, secondarily Hamamatsu NDPI. Evidence: TCGA — the dominant public academic cancer WSI corpus — is 100% SVS ([PMC3822112](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC3822112/)); spatial-transcriptomics-adjacent H&E companion imaging in the literature is repeatedly done on Leica Aperio scanners (e.g. [Nat Commun spatial platform comparison](https://www.nature.com/articles/s41467-025-63414-1), noting "Leica Systems Aperio AT2 scanner, at 40X").
- **Practical build recommendation**: prioritize **OpenSlide** as the reader (covers SVS + NDPI well), accept that MRXS support will be partial/fragile, and explicitly do not plan on iSyntax being readable without a Philips SDK license negotiation.

## Critical Question 1 — What is the single most practical route TODAY for a lab to hand tme-sim a genuine 3D tumour microenvironment?

**Answer: neither serial-section reconstruction (CODA/VALIS) nor cleared-tissue light-sheet imaging is "practical" in the sense of being routine, cheap, or something an average cancer research lab already has sitting on a hard drive. Both are real but boutique, single-lab-scale efforts. Realistic assessment:**

1. **Serial sections + registration (VALIS or a CODA-style pipeline), applied to routine FFPE blocks.**
   - **Cost/effort**: A lab needs a physical block, a microtome for serial sectioning (~4 µm cuts, common core-facility equipment), H&E/IHC staining per section (each section is a normal histology cost, ~$5–20/slide at a core facility, but multiplied by dozens-to-hundreds of sections), a WSI scanner (Aperio-class, already common — this part is *not* the bottleneck), and then registration compute (VALIS is free/MIT and runs on a workstation; CODA needs per-sample DL model training, ~1 day of ML effort per case). CODA's own study used 4,114 sections across 13 samples to reconstruct volumes up to 3.5 cm³ — that is a serious wet-lab undertaking (weeks of sectioning/staining/scanning), not a weekend project.
   - **Who actually does it**: specialized quantitative-pathology/bioengineering labs with dedicated core-facility relationships — e.g., the Wirtz/Wood/Hruban group at Johns Hopkins (CODA), the Gatenbee/Anderson group (VALIS, Moffitt). This is not yet a service a typical GBM tissue bank or neuro-oncology lab offers off the shelf.
   - **Vasculature caveat**: even when done, CODA-style output gives a segmented vasculature *blob*, not a vessel graph — an extra skeletonization step (e.g. running the segmented class through a vessel-graph extractor) would be needed before tme-sim's transport model could use it directly.
   - **GBM-specific**: no evidence CODA has ever been applied to brain/GBM tissue (see Part 2). This route would require a lab to be the first to apply it there.

2. **Cleared tissue (iDISCO/CLARITY/CUBIC) + light-sheet microscopy, processed with ClearMap2/VesselVio.**
   - **Cost/effort**: requires whole-mount or thick-block tissue clearing (days-to-weeks of chemical processing), a light-sheet microscope (expensive, specialized core-facility equipment, far less common than a slide scanner), and immunolabeling optimized for depth penetration. This directly produces a genuine **3D vessel graph with radii** when combined with ClearMap2/VesselVio — output format is a superset of what a transport model needs.
   - **Who actually does it**: neuroscience/vascular-biology labs with light-sheet access (this is a mature technique for whole mouse brains — Kirst et al. *Cell* 2020 processed >20 mouse brains this way) — but applying it to **human** surgical tumour tissue is far rarer, and to GBM specifically, only a couple of groups have published it (Torres-Sánchez 2021, FineVess 2024 — see Part 6), and even they did not release a graph, only qualitative/mask-level segmentation, and neither made data public.
   - **Practical ceiling**: this is genuinely the higher-fidelity route for vasculature specifically (real 3D graph + radius, not a 2D-inferred blob), but it is *less* accessible than serial sectioning because light-sheet imaging is a rarer piece of core-facility equipment than a slide scanner, and human tumour tissue clearing/imaging pipelines are still individual-lab R&D efforts, not services.

3. **A third, more realistic near-term option not in the original tool list**: **stacking 2D Visium/Xenium sections tme-sim already ingests, using PASTE2 or STalign, into a pseudo-3D volume.** This reuses infrastructure tme-sim already has (Xenium/Visium ingestion) and tools already demonstrated on serial ST sections (PASTE2: 16-slice Drosophila embryo reconstruction; STalign: mapping into 3D atlas frameworks). This produces a 3D *transcriptomic/cell-type* volume, not true tissue microanatomy or vasculature — but it is far cheaper to pilot than either CODA-style histology or light-sheet imaging, since it needs only what a lab is likely already generating for Xenium/Visium work (a handful of adjacent sections), not a purpose-built serial-sectioning or clearing campaign.

**Ranked practicality (cost ascending)**: (3) PASTE2/STalign stacking of existing ST sections < (1) VALIS-based serial H&E/IHC registration of new sections < CODA-style full pipeline (expensive, ML-heavy, unproven outside pancreas) < (2) cleared-tissue light-sheet (highest fidelity for vasculature specifically, but requires equipment and expertise most labs don't have, and has essentially never been done for human GBM in a form that produced a usable graph).

## Critical Question 2 — Is there a standard interchange format for "segmented cells with coordinates and classifications"? How many tools would one ingester buy?

**No formal industry standard exists.** This was independently corroborated by two sources: the Digital Pathology Association white paper (PMC8354563) and a 2026 DICOM-in-pathology review (PMC13142108), both stating that DICOM Structured Reporting could in principle encode algorithmic/quantitative pathology outputs but "currently offers limited support" for this, and that cross-platform interoperability today largely still relies on manual/proprietary handling rather than a shared machine-readable schema.

**What exists in practice is a de facto, not de jure, convergence around GeoJSON** for per-object (cell/nucleus/region) geometry + classification + measurement data:
- **QuPath** exports it natively and is the reference implementation.
- **Visiopharm** explicitly documents GeoJSON export and states interoperability with the **10x Genomics Xenium Explorer**, meaning GeoJSON already bridges at least one spatial-transcriptomics platform tme-sim already touches.
- GeoJSON is a generic, RFC 7946-standardized geometry format (not pathology-specific), so any tool that emits polygon/point geometry + a properties dictionary can, in principle, be made to fit this shape even without formally calling it "the pathology standard."

**What one GeoJSON ingester would buy tme-sim**: reliably, **QuPath** (confirmed, documented, testable) and **Visiopharm** (documented, but no public example file to test against, and exact coordinate-column semantics unconfirmed at primary-source level). The other five commercial platforms surveyed (HALO, Aiforia, PathAI, Paige, Proscia, Deep Bio) have **no confirmed GeoJSON or otherwise-standardized per-cell export** — HALO's best-documented route is CSV/FCS (a *different*, well-defined format worth a second, smaller ingester given it's the flow-cytometry standard and thus itself well-specified), and the rest are largely undocumented at the schema level. **Realistic yield: one GeoJSON ingester buys 2 of 8 surveyed tools with confidence (QuPath solidly, Visiopharm probably); a second, small FCS-reader effort would plausibly unlock HALO given enough access to test against; the remaining four (Aiforia, PathAI, Paige, Proscia, Deep Bio) would each need their own bespoke, currently-undocumented integration and cannot be assumed to be GeoJSON-compatible.**

## Critical Question 3 — Has anyone published a publicly downloadable 3D vascular network of human glioblastoma?

**No. This was searched hard, twice, independently, and the negative result was confirmed by an adversarial verification pass. State this plainly: no such dataset exists today.**

What was found, ranked by closeness:

1. **Torres-Sánchez et al., "Three-dimensional vascular microenvironment landscape in human glioblastoma."** *Acta Neuropathologica Communications* 9:20 (2021). PMID: [33579378](https://pubmed.ncbi.nlm.nih.gov/33579378/). DOI: [10.1186/s40478-020-01115-0](https://doi.org/10.1186/s40478-020-01115-0). PMC: [PMC7879533](https://pmc.ncbi.nlm.nih.gov/articles/PMC7879533/). Real human GBM tissue, confocal microscopy of 60 µm sections, quantifies vessel diameter/branching/discontinuities, builds 3D isosurfaces. **Does not construct a computational node/edge graph**, and its data availability statement reads: *"available from the corresponding author on reasonable request."* **Not public.**
2. **FineVess** — deep-learning vessel extraction in 3D confocal images of cleared human glioma tissue (including grade IV/GBM cases). PMID: [38633068](https://pubmed.ncbi.nlm.nih.gov/38633068/), PMC: [PMC11019690](https://pmc.ncbi.nlm.nih.gov/articles/PMC11019690/). Code is public ([github.com/PRBioimages/FineVess](https://github.com/PRBioimages/FineVess)) but output is a **binary segmentation mask, not a graph**, and the underlying data statement reads "not publicly available at this time... available from the authors upon reasonable request." Not public, and even if obtained, not a graph.
3. **Bernabeu et al., "Glioblastoma multiforme restructures the topological connectivity of cerebrovascular networks."** *Scientific Reports* 9:11804 (2019). PMID: [31409816](https://pubmed.ncbi.nlm.nih.gov/31409816/). PMC: [PMC6692362](https://pmc.ncbi.nlm.nih.gov/articles/PMC6692362/). This is exactly the right kind of output — a true vessel graph with radii, ~4.4M segments healthy vs ~1.8M in tumour — **but it is mouse (U87-MG/GL261 xenograft), not human**, and no public data repository was found.
4. **Stolz et al., "Multiscale topology characterises dynamic tumour vascular networks."** *Science Advances* 8:eabm7404 (2022). PMID: [35687679](https://pubmed.ncbi.nlm.nih.gov/35687679/). This has a genuinely public component: **BioImage Archive/BioStudies accession [S-BSST808](https://www.ebi.ac.uk/biostudies/studies/S-BSST808)**, confirmed to contain downloadable NIfTI intravital/ultramicroscopy image zips and analysis code. But it is **mouse tumour vasculature, raw/processed 3D image volumes — not a human dataset and not a pre-extracted graph** (the full >600 GB dataset itself requires an MTA).
5. **VesselGraph** ("Whole Brain Vessel Graphs," Paetzold et al., NeurIPS Datasets & Benchmarks 2021, [arXiv:2108.13233](https://arxiv.org/abs/2108.13233), [github.com/jocpae/VesselGraph](https://github.com/jocpae/VesselGraph)) — the best public *format template*: real downloadable node/edge graphs with radius-derived features (`minRadiusAvg` etc. confirmed present as feature options), CC-BY-NC-4.0 licensed, 11 real + 5 synthetic graphs. **But healthy mouse brain — not tumour, not human.**
6. The adversarial verification pass additionally and specifically checked the **Human Organ Atlas / HiP-CT** (human-organ-atlas.esrf.eu, real synchrotron whole-human-organ imaging including 65 brain datasets) and found **zero brain tumour specimens and zero vessel segmentations deposited anywhere in the archive** (confirmed: the HOA paper itself states segmentations are "future work"). It also checked the Image Data Resource (0/147 relevant projects) and the Brain Image Library (0/14,033 datasets) by full index, not just keyword search, and found nothing. Two Zenodo records that looked promising (ONCOhabitats TCGA-GBM/Ivy-GAP, 4704090/4704106) turned out to be access-restricted MRI perfusion-habitat voxel maps, not vessel graphs, even before considering they aren't vasculature data.

**Plain statement: there is currently no public, downloadable, 3D vascular network graph (or even a downloadable segmented 3D vasculature mask) of human glioblastoma anywhere in the literature or major public repositories searched.** The two labs that have generated the closest real human-GBM 3D vascular data (Torres-Sánchez, FineVess) both explicitly offer "reasonable request" access — email is the only currently viable route to real human GBM vascular geometry, and even then FineVess only yields a mask, not a graph (would need vessel-graph extraction, e.g. via VesselVio, run afterward).

## Ranked, costed recommendation: top 3 ingestion targets for tme-sim

**#1 — QuPath GeoJSON cell-detection export.**
*Cost*: Low. Format is documented, MIT/GPLv3-adjacent open ecosystem, multiple real example files already downloadable from public GitHub repos ([kbestak/QuPath_Annotation_to_Quantification_file](https://github.com/kbestak/QuPath_Annotation_to_Quantification_file), [choosehappy/QuPathGeoJSONImportExport](https://github.com/choosehappy/QuPathGeoJSONImportExport)), no wet-lab or vendor-access dependency to start building and testing an ingester today. QuPath is also the most widely used open pathology tool in academic cancer research, so building this ingester has the highest probability of matching what a real collaborating lab can hand over.
*Effort*: A parser for GeoJSON `FeatureCollection` → per-cell polygon/centroid + `classification` + `measurements` properties. Can reuse existing GeoJSON libraries; the main work is mapping QuPath's classification taxonomy onto tme-sim's internal cell-type schema.
*Payoff*: Directly buys per-cell spatial + classification data from any lab running QuPath — the single most common open pathology quantification pipeline — and is a plausible stepping stone to Visiopharm (same GeoJSON shape, per its documentation) with modest extra validation effort.

**#2 — VALIS-based serial-section stacking of QuPath outputs (2D→2.5D/3D pipeline), i.e. build the ingester to accept a VALIS-registered OME-TIFF stack + per-section QuPath GeoJSON, warped through VALIS's own coordinate-warping API.**
*Cost*: Moderate. VALIS is free/MIT, runs on a standard workstation (no light-sheet/clearing equipment needed), and a lab only needs to hand over a modest stack of already-common serial sections (VALIS has been validated down to real tumour IHC/IF stacks of 2–69 images). This is realistically the **cheapest real 3D route** available today (see Critical Question 1), even though it does not natively produce vasculature — it reconstructs 3D positions of cells/regions from stacked, per-section QuPath (or similar) segmentation.
*Effort*: Ingester needs to (a) read VALIS's output OME-TIFF pyramid + transform metadata, (b) apply VALIS's coordinate-warping to per-section QuPath cell tables to place them into a shared 3D coordinate frame. This is a bigger lift than #1 (multi-section alignment logic) but reuses #1's per-section parser directly.
*Payoff*: Turns tme-sim from a single-2D-section tool into a genuine (if coarse, no true vasculature) 3D-microenvironment tool, using infrastructure a collaborating lab could plausibly generate on a modest budget (standard serial sectioning + standard WSI scanning + free software) rather than requiring rare light-sheet equipment or an unproven CODA-style ML pipeline.

**#3 — ClearMap2/VesselVio vessel-graph format (GraphML/attributed-graph with per-segment radius), as a forward-looking target rather than an immediate build.**
*Cost*: High to obtain real data (light-sheet equipment, tissue clearing, and — critically — no existing public human GBM dataset in this format; see Critical Question 3), but **low to build the ingester itself**, since the target schema (nodes = branch points, edges = vessel segments with radius) is simple, well-documented, and open source on both the segmentation side (ClearMap2) and the analysis/export side (VesselVio, GPL-3.0). Public mouse-brain vessel graphs (VesselGraph, CC-BY-NC-4.0, [github.com/jocpae/VesselGraph](https://github.com/jocpae/VesselGraph)) are downloadable **today** and could be used to build/test the ingester as a non-tumour, non-human proxy while waiting for real tumour data.
*Effort*: Parser for an attributed graph (nodes with 3D position, edges with radius/length/tortuosity) — this is closer to tme-sim's actual physics-model input shape than either cell-coordinate table above, since a transport model wants vessel topology + radius directly.
*Payoff*: This is the *right* long-term target — it is literally the data structure tme-sim's transport physics wants — but building it now means building against a proxy (healthy mouse brain) since no human GBM version exists publicly. Recommend building this ingester against VesselGraph's mouse data now (cheap, real, well-specified) so that the day a lab either releases FineVess-style human GBM segmentation data or completes a light-sheet GBM vasculature study, tme-sim can ingest it immediately rather than starting from zero. Practically, also worth directly emailing the FineVess (PMC11019690) or Torres-Sánchez (PMC7879533) corresponding authors now — both explicitly offer "reasonable request" access, and FineVess in particular has already done the hard segmentation work on real human grade II–IV glioma tissue.

**Not recommended as near-term targets**: the remaining commercial platforms (HALO, Aiforia, PathAI, Paige, Proscia, Deep Bio) — no public schema, no test data, and access itself requires an institutional/commercial relationship that doesn't yet exist; and CODA specifically — powerful and directly on-topic in spirit, but unproven outside pancreas, requires per-sample ML training, produces only a voxel-blob (not a graph) for vasculature, and its underlying data is not public.

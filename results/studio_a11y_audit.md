# tmesim Studio — keyboard-navigation and screen-reader-semantics audit

Cross-cutting a11y pass over the whole front end (`app/web/`), run against the
real backend (`./.venv/bin/python -m app.server`, real run history, real
mechanism attribution, real caveats — no mocked data). Driven headlessly with
`playwright-core` against the cached Chrome-for-Testing binary
(`~/Library/Caches/ms-playwright/chromium-1234/...`, software WebGL via
`--use-angle=swiftshader`), plus `page.accessibility.snapshot()` and computed-style
contrast sampling. Scripts live in the session scratchpad, not in this repo.

This ran alongside three other agents working the viewer/canvas
(`app/web/js/gl/`), the protocol editor (`app/web/js/editor/`,
`ui/protocol.js`), and reports/projects/history (`ui/reports.js`,
`ui/projects.js`, `ui/history.js`). Per scope, fixes in this pass are surgical
and localized; anything larger found in one of those three owned areas is
reported below as a follow-up rather than patched here.

## 1. Inventory — what was actually found, before any fix

| # | Surface | Issue | Severity | Where |
|---|---|---|---|---|
| 1 | RunSpec JSON editor (SETUP rail, `#spec-editor`) | Hard keyboard trap. `Tab` was unconditionally captured to insert two spaces, with no `Shift+Tab` or `Escape` handling at all — once focused, `Tab` could never leave the field. Reproduced directly: an automated `Tab`-only traversal got stuck on this exact element. | **High** | `app/web/js/ui/spec.js` (unowned) |
| 2 | Protocol workspace (`P`, or the `protocol` launcher) | `Esc` did not reliably close it, contradicting the app's own normative contract (`docs/UI_ARCHITECTURE.md` §2.7: "`Esc` closes it"). Root cause: the TPL editor has focus immediately on open (`show()` calls `editor.focus()`), and its own `Escape` handler (`js/editor/editor.js`) calls `stopPropagation()` before blurring itself — so the workspace's own `Escape`-closes-it listener on `root` (a *descendant* of `<body>`) never sees the key. After the blur, focus lands on `<body>`, which is an *ancestor* of `root`, so no amount of further `Escape` presses could ever reach that listener; each one instead fell through to the app's Escape handling of the *rendered-but-invisible* viewer underneath. Confirmed empirically: two consecutive `Escape` presses after opening, still open, both times. | **High** | `app/web/js/ui/protocol.js` + `app/web/js/editor/editor.js` interaction; fixed from `app/web/js/main.js` (unowned) |
| 3 | Run history dock (`ui/history.js`) | The whole `<tbody>` (up to dozens of `<tr>`, two of them focusable per row) is destroyed and rebuilt from scratch on **every** 6-second background poll (`setInterval(refreshRuns, 6000)` in `main.js` → `history.setRuns()` → unconditional `render()`), whether or not the run list actually changed. Any keyboard focus inside the table at that moment is lost to `<body>`. A keyboard user who pauses on a row — which is easy, since there can be 30+ rows each with 2 tab stops — will silently lose their place, with no announcement, on a strict 6 s clock. Same pattern in the Therapy reports dock (`ui/reports.js`), polled every 2.5–15 s. | **High** (real, reproducible, and ambient — happens continuously whenever the app is idle) | `app/web/js/ui/history.js`, `app/web/js/ui/reports.js` (**owned by the reports/projects/history agent — not fixed, see §3**) |
| 4 | Projects workspace — delete/detach buttons | Three icon-only buttons (delete project, remove specimen, detach run) had only a `title` attribute and a literal `×` glyph as their only content. Per the accname algorithm, visible text content wins over `title`, so their accessible name was the character "×" (read as "times"/"multiplication sign" by a screen reader), not the destructive action it performs. | **Moderate** | `app/web/js/ui/projects.js` (owned, but this is exactly the "add one missing aria-label" class of fix the scope allows) |
| 5 | Mechanism legend collapse button | `aria-label` stayed `"Collapse the mechanism breakdown"` even after the button was clicked and the panel was already collapsed — only the glyph and `aria-expanded` flipped, not the label. `aria-expanded` still carried the correct state, so this wasn't misleading, just imprecise. | **Low** | `app/web/js/ui/mechanism.js` (unowned) |
| 6 | RunSpec form validation errors | `aria-invalid` was already (correctly) set on the real focusable control, not a wrapper — but the adjacent error text (`.field-err`) had no `id` and nothing pointed `aria-describedby` at it, so a screen reader landing on an invalid field announced only "invalid," never *why*. There was also no live region, so a validation pass that flags a field the operator isn't currently on announces nothing. | **Moderate** | `app/web/js/ui/spec.js` (unowned) |
| 7 | RunSpec form — 4 segmented-control fields | `sensitivity_mode`, `vascular_mode`, `oxygen_mode`, `state_mode` are not in the backend-error→field `idFor` map at all, so a server-side validation error on one of those paths never reaches its row (only the top diagnostics list). Pre-existing completeness gap, not something this pass introduced or touched. | **Low** (feature gap, not strictly an a11y regression) | `app/web/js/ui/spec.js` — **not fixed**, flagged only |
| 8 | Colour contrast — `--fg-3` ("disabled, placeholder") used for live info | Used for the specimen one-line description in the top bar (`#hdr-section-meta`) and the site-wide `.dim` utility class, both of which carry real, readable content (not disabled/inert). Measured **2.51:1 (dark) / 2.65:1 (light)** against their panel backgrounds — roughly half of the WCAG AA 4.5:1 floor for normal text, in both themes, everywhere `.dim` is used. | **High** (severity of the gap), but token-level / app-wide blast radius | `app/web/css/tokens.css` (`--fg-3`) — **not fixed**, see §3 |
| 9 | Colour contrast — `--fg-2` ("labels, units, captions") near the AA line | Same token, two different near-misses depending on background: **4.25:1** in light theme against the rail panel background (affects field labels, units, `hr-lbl` dividers, metric labels), and **4.38:1** in dark theme against the status bar / table-header background. Both just under the 4.5:1 floor. | **Low–Moderate** (small margin, but the token is used very widely) | `app/web/css/tokens.css` (`--fg-2`) — **not fixed**, see §3 |
| 10 | Colour contrast — segmented-control inactive text | **4.38:1** in dark theme (same `--fg-2` family, against `--bg-0`). | **Low** (borderline) | `app/web/css/tokens.css` / `components.css` — not fixed |
| 11 | Colour contrast — `.chip.computed` provenance chip | **4.17:1** in light theme (info-blue on its own tinted background). `.chip.measured` and `.chip.assumed` both clear AA comfortably in both themes. | **Low** (borderline, one of three chip kinds, one theme) | `app/web/css/tokens.css` (`--info`) — not fixed |
| 12 | `.chip.st-failed` / `.chip.st-running` run-status chips | Sampled **≈4.25–4.28:1** in both themes, i.e. borderline-under AA — but this reading is lower-confidence: no failed/running run existed in the live session to sample directly, so these were measured from a synthetically-injected same-class node outside their real table/status-bar context, which can shift the composited background. Flagged for a targeted manual re-check, not asserted as a confirmed failure. | **Low (unconfirmed)** | `app/web/css/components.css` — not fixed, follow-up only |
| 13 | Help/keys native `<dialog>` | One intermediate `Tab` stop during traversal briefly lands on `<body>` (no visible focus indicator for that single stop) before wrapping back into the dialog's own controls. Root cause not conclusively isolated (candidate: Chromium's "keyboard-focusable scroller" behavior on the scrollable `.keys-body` content, interacting with headless/software-GL rendering) — low impact, not fixed. | **Low** | native `<dialog id="help-dlg">` in `index.html` |
| 14 | Run-history rows: one `Tab` stop per row | Every row carries `tabindex="0"` (34 rows in this session = up to 68 tab stops just to pass through the dock), rather than the ARIA APG "roving tabindex" pattern (single stop, arrow-key row-to-row navigation) — which is actually implemented for arrow-key movement already (`ArrowUp`/`ArrowDown` on a focused row moves to the neighbour), just not exclusively: every row is *also* independently reachable by `Tab`. | 15 | `.proj-item` (project / specimen rows, Projects workspace) | `tabindex="0"` + `onkeydown`(Enter/Space) but no explicit `role="button"`, unlike the equivalent pattern used for the mechanism-legend rows (`role="button"` there). Accessible name still resolves correctly from visible text content, so this works, just inconsistently with the rest of the app. | **Low** | `app/web/js/ui/projects.js` (owned) — not fixed, follow-up |

### Verified correct (no fix needed — stated so this isn't read as an all-negative pass)

- **Native `<dialog>` usage** (help/keys, projects, report viewer) gives correct focus containment, `Escape`-to-close, and focus-restored-to-launcher *for free*, confirmed by direct interaction on all three.
- **Zero unnamed interactive nodes** in `page.accessibility.snapshot()` across four surfaces (main shell, help dialog, projects dialog, protocol workspace) — every button, link, checkbox, combobox and slider found had a non-empty accessible name.
- **`prefers-reduced-motion`**: grepped every `transition` / `animation` / `@keyframes` in `app/web/css/*.css` (23 rules total, confined to `base.css`, `layout.css`, `components.css`, `protocol.css`; `mechanism.css`, `reports.css`, `projects.css`, `tokens.css` have none). `base.css`'s reduced-motion block is specifically engineered against the documented "1 ms turns a pulse into a strobe" failure mode: it sets the blanket 1 ms override *and* explicitly kills the three looping/pulsing elements (`.spinner`, `.led.busy`, `.progress.indet > i`) and the two moving-bar transitions (`.progress > i`, `.pcell .bar`) outright. No JS-driven opacity/transform loop exists outside the WebGL canvas's dirty-flag render loop (idles at 0% GPU per its own contract, confirmed in `gl/viewer.js`) and the user-initiated, pausable time-lapse scrubber (`setInterval` in `ui/mechanism.js`, gated behind an explicit Play button, not autoplaying). **No strobe risk found anywhere**, old or new.
- **Colour is not the only channel**: mechanism-legend rows, provenance chips, and run-status chips all carry a text word alongside their colour, confirmed in the accessibility tree, matching `docs/UI_ARCHITECTURE.md` §4.5.
- **Toast notifications** (`role="log"`, `aria-live="polite"`) correctly announce run-queued / run-done / run-failed and explicit validate/network errors.
- **Hover/pinned cell read-out** (`role="status"`, `aria-live="off"`) is a deliberate choice, not a bug: it updates on every mouse-move over the canvas, and an active live region there would spam a screen reader continuously.
- **Tab order** through the whole app (top bar → SETUP rail DEFINE → COMMIT → stage toolbar → canvas → mechanism legend → time-lapse scrubber → splitters → READ rail groups → RUNS dock) is spatially logical and matches the zones in `docs/UI_ARCHITECTURE.md` §2 — no unpredictable jumps found.
- **Full baseline test suite** (`./.venv/bin/python -m pytest tests/ -q`) — **552 passed** before this pass. Re-run after fixes below.

## 2. Fixes made (all surgical, single-file or single-function)

1. **`app/web/js/ui/spec.js` — closed the RunSpec-editor keyboard trap.** Added an `Escape` branch to the existing `onkeydown` that blurs the textarea, mirroring the convention `js/editor/editor.js` already uses for the TPL editor. `Tab` still claims indentation (same convention, both editors), but there is now always a keyboard-only way out.
2. **`app/web/js/main.js` — restored "`Esc` closes every workspace."** Added a fallback at the top of the global `Escape` case: if `window.__tmesimProtocol.visible` is true, hide it and stop, before falling through to the viewer's tool-clear/unpin handling. `window.__tmesimProtocol` already existed for this exact purpose (documented in `protocol.js` as "a headless driver has to be able to reach the plan step without synthesising a click"). Fixes the case where focus has landed on `<body>` after leaving the TPL editor, which `protocol.js`'s own `root`-scoped listener structurally cannot reach.
3. **`app/web/js/ui/protocol.js` — `hide()` now restores focus to the `protocol` launcher button**, matching what the two native-`<dialog>`-based workspaces already do for free. One line (`b.focus()`), no visual change.
4. **`app/web/js/ui/projects.js` — added `aria-label` to the three icon-only `×` buttons**: `Delete project {id}`, `Remove specimen {id}`, `Detach run {id}`.
5. **`app/web/js/ui/mechanism.js` — the collapse button's `aria-label` now flips with state**, same convention as its own `aria-expanded` and glyph (`Collapse the mechanism breakdown` ↔ `Expand the mechanism breakdown`).
6. **`app/web/js/ui/spec.js` — wired validation errors for assistive tech.** Each field-row's error `<div>` now has a stable `id` (`{fieldId}-err`) and `role="alert"`; the paired control gets `aria-describedby` pointing at it. A screen reader now (a) reads the specific reason when it lands on an invalid field, and (b) hears the error the moment validation fills it in, even if focus is elsewhere. Verified end-to-end against the real backend: an actually-invalid `total_time_s: -100` round-tripped through `POST /api/validate` and produced `aria-invalid="true"`, `aria-describedby="f-total-err"`, and error text `"must be > 0, got -100.0"` in the live DOM.

Verified after each fix with the same headless-Chrome harness (not just read back): the two-`Escape` protocol-workspace close, the editor's Tab-then-Escape-then-Tab-continues sequence, the projects dialog's accessible names via `page.accessibility.snapshot()`, and the validation round-trip above.

## 3. Follow-ups for the owning agents (found, not fixed — out of surgical scope here)

**reports/projects/history agent** (`ui/history.js`, `ui/reports.js`, `ui/projects.js`):
- **#3 above is the highest-priority item in this whole audit.** The run-history dock (and, less severely, the reports dock) rebuild their entire row list unconditionally on every background poll, dropping keyboard focus to `<body>` if it was inside the table. Minimal fix shape: skip `render()`/`renderList()` when the fetched list is referentially/deeply unchanged from the last render, or — if a change did occur — capture `document.activeElement`'s `run_id`/row before `clear(tbody)` and refocus the equivalent new row afterward.
- #14: consider roving `tabindex` (one row in the tab sequence at a time; arrow keys already move focus between rows) to cut ~2×N tab stops down to a small constant.
- #15: add `role="button"` to `.proj-item` for consistency with the rest of the app's tabindex-0-div convention (`m-row` already does this).

**No findings requiring action were found in `app/web/js/gl/` (viewer/canvas)** — the canvas itself is correctly `tabindex="0"` with a descriptive `aria-label`, and its render loop is confirmed dirty-flag-driven with no continuous-motion a11y risk.

**No further findings requiring action were found in `app/web/js/editor/` or `ui/protocol.js`** beyond the interaction described in #2, which was fixed from the unowned `main.js` without touching either owned file.

**Cross-cutting / token-level (nobody's single ownership, high blast radius — reported, not patched by this pass):**
- #8: `--fg-3` is documented in `tokens.css` as "disabled, placeholder" but is applied to live, readable information (`#hdr-section-meta`, the generic `.dim` class used across every panel in the app). Recommend either lightening `--fg-3` itself enough to clear 4.5:1 against `--bg-0`/`--bg-1` in both themes, or introducing a distinct token for "de-emphasized but readable" text and reserving `--fg-3` for genuinely inert/disabled controls (which are exempt from the contrast requirement). Either change touches every consumer of `--fg-3` across all panels, including the three owned areas — a token retune, not a localized fix.
- #9/#10: `--fg-2` is a few percent under AA against two of its several real backgrounds (light-theme rail panel, dark-theme status bar). Small margin; likely fixable with a 1–2% lightness nudge, but still a shared token.
- #11: `--info` (used by `.chip.computed`) is a few percent under AA in light theme only.
- #12: `.chip.st-failed` / `.chip.st-running` — re-check directly against a real failed/running run rather than the synthetic sample used here.
- #13: the one `<body>`-focus stop inside the help dialog's tab cycle — low impact, root cause not conclusively isolated; worth a look if the "focus is visible on everything" contract is being re-verified in a future pass.
- #7: the 4 segmented-control RunSpec fields not routed through the backend-error→field map — a validation-completeness gap that happens to also mean those 4 fields never get `aria-describedby`d; whoever owns RunSpec validation should decide whether to extend `idFor`.

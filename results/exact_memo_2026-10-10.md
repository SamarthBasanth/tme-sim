## 0. Verdict up front

**Both are exact, neither is a model, and the second one is exact in a narrower
sense than yesterday's record implied.**

| | what it answers | error against a re-solve (measured at `dx = 30`, §5) | cost (measured at the shipped `dx = 12`, §6) |
|---|---|---|---|
| **exact memo** | a spec already solved under the same engine | **zero — bit-identical across every numeric leaf of the stored record** | 0.181 ms against 62.96 s |
| **algebraic scaling** | a spec never solved, differing only in dose and/or half-life | **0 ulp on 7 of 19 served readouts, ≤ 14 ulp (1.676e-15 relative) on the other 12, at a dose ratio of 3** | 0.601 ms against 65.09 s |

The two columns are two different measurements and are labelled as such: the
accuracy was scored at `dx = 30 um` where a re-solve is cheap enough to run
four of, and the cost at the `dx = 12 um` the product ships.

The memo's value is not the speed. It is that **a repeat currently re-solves**,
and a re-solve of a spec whose answer is already stored is a minute of CPU
spent reproducing a number this repository can already prove it has. The risk
is not the speed either: it is a stale hit, and §2 and §3 are about nothing
else.

## 1. What is actually new

There was no RunSpec-keyed run cache — only the reconstruction cache
(`app/server/cache.py::RECON_CACHE`) — so `POST /api/runs` on a spec solved
five minutes ago re-ran the whole chain. There is now a lookup, behind one new
route, and it is a lookup and not a hook: **`POST /api/runs` is unchanged.** A
memo on the submit path would make a second click return the first click's
`run_id`, and changing what a shipped surface records is not a decision a cache
gets to make on its own.

Every completed run now stamps `provenance['memo']` with two digests. A run
with no stamp — every run in `app/runs/` written before this — is **never** a
memo candidate, which is the only honest answer about a run whose engine state
nobody wrote down.

## 2. The key, component by component

Six components. Each answers a different way a stored answer stops being the
answer.

| component | what it is | what it protects against |
|---|---|---|
| `memo_format` | an integer in `memo.py` | a change to the canonicaliser being read as a match |
| `spec_digest` | the RunSpec, canonicalised | two different runs reducing to one key |
| `solver_constants` | `PDE_DT_S`, `PDE_SAVE_EVERY`, `PDE_CONVECTION`, `SIM_SEED`, `DEFAULT_TIMELAPSE_FRAMES`, `TIMELAPSE_BUDGET_BYTES`, read live off `jobs.py` | the frozen RunSpec carrying no solver settings, so the spec alone does not pin the run |
| `engine` | sha256 over every `.py` under `tmesim/` (143 files) and eight named `app/server/` modules, plus `calibrate_alpha()` to full repr, plus the numpy / scipy / CPython versions | the engine's numbers moving |
| `tissue_digest` | `cache.py`'s own `_fingerprint` over the section's metadata source files, hashed | the specimen at the path changing |
| `claim_set_version` | `jobs.CLAIM_SET_VERSION` | a withdrawn claim being laundered |

**Canonicalisation is total and conservative.** Every key participates, nulls
included. It normalises exactly two things that provably cannot change a run —
key order, and the int/float spelling of one number, because `execute_run`
coerces every numeric field with `float()`. It does **not** resolve an omitted
field to its default, so `{}` and `{"timelapse_frames": 24}` are two keys for
one run. That costs a MISS, which is free; the opposite error is the one that
puts a wrong number on a screen. Every doubtful case is resolved towards the
miss, and an unrepresentable value (a non-finite float, an integer past
2^53) is REFUSED rather than approximated into a key.

The null case is not hypothetical arithmetic: `execute_run` reads
`spec.get("timelapse_frames", DEFAULT_TIMELAPSE_FRAMES)` and then
`int(x) if x is not None else 0`, so an explicit `null` means **zero** frames
and an absent field means **24**. A canonicaliser that tidied nulls away would
merge them. That defect was planted and the suite went red (§8).

**Two guards on the claim set, because they catch different things.** The
version is in the KEY, so a withdrawal turns every memo into a miss and a
repeat re-solves into compliant caveats. And `memo_lookup` ALSO re-runs
`claim_set_status` on each candidate and refuses anything SUPERSEDED or
CONTRADICTED. The second catches what a version comparison cannot: a record
stamped with the current claim set whose caveats still carry a sentence that
claim set retired. `r_00090` in `app/runs/` is the real specimen, retained
deliberately by `tests/test_claim_set.py`, and on an era check alone it reads
CLEAN.

**The hash is taken out of the trust chain where it can be.** A key match is a
sha256 comparison, and for the SPEC half that is not necessary: the stored run
carries its own spec, so the candidate's canonical spec is compared for
EQUALITY as well. The same is done for the shape key, where everything outside
the two scaled axes must be byte-identical after canonicalisation. It cannot be
done for the other components — an engine fingerprint is a digest by
necessity — but it costs nothing here and removes one assumption.
`tests/test_memo.py::TestExactMemo::test_a_key_match_alone_is_not_enough`
forges a matching key onto a different spec's run and asserts the lookup
refuses it.

A hit is served through `Job.result_view()`, so the claim-set verdict and the
pruned-payload reconciliation are computed on **that read**, exactly as they
are for `GET /api/runs/{id}`. Nothing is copied from the record that is a fact
about the reader's moment.

## 3. The residual staleness risk, stated as gaps

A guard whose gaps are unlisted reads as a guarantee. Four gaps, in the order
they are likely to bite:

1. **Input data is not hashed.** No expression matrix, compound library file or
   ingest registry entry enters the key. `tissue_digest` is (size, mtime) over
   the section's METADATA files only — it would not see an edit to a matrix
   inside a Visium directory. **The closure exists and is not built here:** a
   memo could rebuild the reconstruction (cheap, and `RECON_CACHE`-backed
   anyway — `results/surrogate_feasibility_2026-10-09.md` §7 measures
   reconstruction at a 1.79 s median against a 58.77 s solve at `dx = 12`) and
   require the stored `report` block to match bit-for-bit before serving the
   metrics. That would make a changed input a miss rather than a hit.
2. **The numerical environment.** A different BLAS, thread count or CPU can
   change a reduction order. Nothing in the key sees that.
3. **Source on disk is not bytecode in memory.** The fingerprint is computed
   once per process and cached, deliberately: it should describe the code that
   is RUNNING, which is whatever was imported. It cannot notice a reloader that
   re-imported one module in place.
4. **Anything outside the hashed set.** A new module under `app/server/` that
   reaches a run's numbers and is not in `memo._ENGINE_FILES` is invisible.
   `tests/test_memo.py` pins that list against the `engine_entrypoints` a run
   records about itself, so a new entry point in the chain fails the suite
   rather than quietly weakening the key.

**So the honest claim is narrow:** a stale hit now requires an unhashed input,
an unhashed module, or a changed numerical environment. It is not impossible.

**What it costs to be this conservative.** `memo.py` and `memo_api.py` are
themselves in the hashed set, so editing a COMMENT in either invalidates every
stored memo. That is deliberate — a change to the canonicaliser MUST
invalidate, and a format version only does that when a human remembers to bump
it. It was observed in development: an edit to one docstring turned every hit
in a test store into a miss. The cost is paid in re-solves, which is the safe
direction.

## 4. The algebra, re-derived from the engine

### 4.1 Why there is an identity at all

In the shipped (`time_resolved = False`) path, **every PK number a user can set
reaches the transport solve through one float.** `tmesim/sim/engine.py` computes
`plasma_mean = plasma_profile(pk, times).mean()` and then
`source = delivery_source(work, drug, plasma_mean)`; nothing else about the
schedule is passed down. `plasma_profile` is exactly linear in
`pk.plasma_peak` (`contrib = pk.plasma_peak * exp(-lam * elapsed)`), and the
transport PDE, its first-order sink and the steady-state reach solve are all
linear in the source with `C(0) = 0`.

So the concentration field is **homogeneous of degree 1 in that one scalar**:
every ratio of exposures is invariant and every exposure magnitude is
proportional. The scale factor is computed by calling the engine's own
`plasma_profile` on the engine's own time grid, and the recomputed value for
the STORED run's PK block is then required to equal the `plasma_mean_uM` that
run recorded **bit for bit** — otherwise the lookup refuses. That check is what
makes a moved PK model, time grid or default a miss instead of a wrong factor.

**The reach block is PK-independent by construction, not by measurement.**
`app/server/reach.py` solves the steady-state field from a UNIT source
(`delivery_source(micro, drug, 1.0)`), so `E_ref`, the headline and all seven
rungs carry no PK input at all. The 0 violations yesterday's record measured on
the ladder are confirming a structural fact, which is a stronger statement than
the one it was reported as.

### 4.2 THE CORRECTION: "exactly 4.0" is true BECAUSE 4 is a power of two

`results/surrogate_feasibility_2026-10-09.md` §3 reports that a 4x
`plasma_peak` change leaves `E_p90/E_p10` **bit-identical** and moves `E_p50`
by **exactly 4.0**, and summarises the axis as "EXACTLY null". Every one of
those numbers is correct. The summary generalises further than they support,
because **that sweep only ever used a ratio of 4.0, which is a power of two**,
and scaling an IEEE-754 double by a power of two is exact.

Measured today on real solves — `probe_scaling.py`, 5 (section, compound) cases
over `gbmspace_at12_bra_4_fo_4_1` and `xenium_breast` with temozolomide,
doxorubicin and vincristine, 7 arms each, 35 solves, at dose ratios 4.0, 1.5
and 3.0 and half-life ratios 4.0 and 1.37:

* at a ratio of **4.0**: every shape readout is bit-identical and every
  magnitude readout lands on exactly 4.0, reproducing §3;
* at **1.5x** and **3x**: the same readouts are 1–27 ulp away. `E_p50_uM`
  reads a fold of `1.4999999999999996` where 1.5 was asked for, and
  `penetration_index` — bit-identical at 4x — reads `0.9999999999999963`.

This is the same lesson `app/server/reach.py::SCALE_INVARIANCE_NOTE` already
records for `bbb_penetrance`: *"EXACT IN EXACT ARITHMETIC ... an earlier
wording of this clause said 'bit-identical' about all of them, which is false
for two."* The dose axis has the identical structure, and the structure was
hidden by the choice of sweep.

**What this changes in practice: nothing numerical, and one word.** 27 ulp is
~6e-15 relative, far below anything this repository claims. What it changes is
that a dose slider cannot be advertised at ZERO error in general. So the
response reports `bit_exact` **per request** — true only when the change is
dose-only and the realised ratio is a power of two — and carries the measured
ulp bound per readout otherwise.

The half-life axis was never bit-exact and §3 already shows it: the
`1.0000000000001659` it reports for the spread under a 16x change is 1.7e-13,
not zero.

### 4.4 What is refused, with the measured reason

Refusal is the default: **a leaf not in the table above is refused**, so a
metric added to `execute_run` is refused until somebody measures it.

| refused | measured dose fold | measured half-life fold | why |
|---|---|---|---|
| `kill_fraction` | 1.0021 – 1.9959 | 1.0001 – 1.0474 | a Hill function of exposure. **And an absolute kill fraction is never a defensible output of this product**, so it is not a cache or scaling feature under any arithmetic |
| `therapeutic_coverage_1x` | 1.0 – 8.1109 | 1.0 – 1.5590 | counts cells crossing a FIXED IC50 threshold |
| `therapeutic_coverage_2x` | 1.0003 – 3.4403 | 1.0 – 1.0743 | same |
| `therapeutic_coverage_0_5x` | 1.0 – 1.3185 | 1.0 – 1.0561 | same |
| `viable_tumor_fraction` | 0.2111 – 0.9867 | 0.9267 – 0.9991 | a post-kill cell count |
| `penetration_length_um` | ≤ 1.049e+07 ulp (3.5e-9 rel) | ≤ 1.147e+07 ulp | the length IS invariant; it is read off an `exp + floor` least-squares FIT that amplifies round-off. `reach.py::SCALE_INVARIANCE_NOTE` measures this same fitted length moving **2.9e-05 relative at dx = 30** under a pure global source multiplier, so a 3.5e-9 reading on two sections is not a bound |
| `mechanism`, `timelapse` | — | — | a kill partition, and a binary payload a scaled answer does not have |

**Axes refused, not just readouts.** `total_time_s` is not scalable at all: it
moves the integration window as well as the plasma average, and
`axis_exponents.py` measures `median_tumor_auc` at 8.93x and `E_p10_uM` at

interesting case: by §4.1's derivation they reach the solver only through
`plasma_mean`, so they *should* scale exactly — and **every row of the
measurement carries `n_doses = 1`.** A derived-but-unmeasured identity is not
an exact answer, so the code refuses them, and the refusal is asserted. That
widening was planted and the suite went red (§8).

## 6. Cost

A performance claim is a claim, and
`results/performance_profile_2026-09-20.md` §0.1–0.2 records one RunSpec on
unchanged code measuring five different wall-clocks on this machine. Ratios are
the part to quote, and the load is given.

`xenium_breast`, `dx = 30 um`, 6 h window, loadavg 1.8–2.1 on 10 CPUs:

| | measured |
|---|---|
| solve, cold (reconstruction included) | 9.73 s |
| solve, warm (reconstruction cached), twice | 6.94 s / 6.98 s |
| **exact memo hit** | **0.174 ms** → **3.99e4 x** the warm solve |
| **algebraic answer, 3x dose, never solved** | **0.514 ms** → **1.40e4 x** its own solve (7.17 s) |

The same spec at the resolution the product actually ships, `dx = 12 um`,
loadavg 2.3–3.5 on 10 CPUs — note the cold solve is the FASTEST of the three
here, which is the load talking and is why the ratio is the quotable part:

| | measured |
|---|---|
| solve, cold | 57.12 s |
| solve, warm, twice | 63.56 s / 62.96 s |
| **exact memo hit** | **0.181 ms** → **3.48e5 x** the warm solve |
| **algebraic answer, 3x dose, never solved** | **0.601 ms** → **1.08e5 x** its own solve (65.09 s) |

The engine fingerprint costs **0.849 s once per process** (143 source files
hashed) and is then free; a warm key costs **0.101 ms**. Nothing is billed per
request except the lookup.

**What the ratio is not.** It is not a claim about a run. A memo hit replaces a
run that has already happened once; the saving is real only on a repeat, and
the algebraic answer's saving is real only along two axes. Neither makes the
solver faster.

## 7. Honesty on the surface itself

* A memo hit and a fresh solve **agree on every number**, asserted bit-for-bit
  over more than a hundred leaves. They do not agree on provenance: a hit
  carries the ORIGINAL execution's `run_id` and timestamps, and its payload
  endpoints point at that run's files. So the response carries `is_solve: false` and a `disclosure`
  naming the run it recalled. It is phrased as "this is not a solve" and not as
  `cached: true`, because *cached* invites the reading that the number might be
  stale — and the key in §2 exists to make that the one thing it cannot be.
* **An algebraically scaled answer is not a solve, and asking for one is
  opt-in.** `allow_scaling` defaults to false. A caller that asked whether the
  answer was already known, and silently received a rearrangement of a
  different run, would have been told something it did not ask about.
* **A pruned payload is never reported present.** `payload_status` stats the
  filesystem rather than trusting `pruned_payloads`, so it separates four
  states — present, pruned (with the date and byte count), **missing** (gone
  with no prune recorded: a bare `rm`, a partial copy, a failed restore), and
  never produced. The `missing` state exists because
  `scripts/prune_run_payloads.py`'s whole premise is that `rm` leaves the
  server explaining confidently that the payload was never captured. Where two
  stored copies of one spec exist, the memo prefers the one whose payloads are
  still on disk, and reports `complete: false` when none is.
* **No ordering between compounds is produced.** The route answers one spec.
  The cross-compound ranking was withdrawn on 2026-08-21 and nothing here
  reinstates it. `verdict_stability` — which compound keeps its delivery/dose
  verdict under the transvascular term the transport law lacks — is copied
  verbatim onto every scaled answer, because a delivery number read without it
  could belong to one of the seven compounds in twelve whose verdict inverts.

## 8. Every guard was confirmed to bite

Eight defects planted, each confirmed to parse and to be REACHED before the
suite was run, each reverted and the file compared byte-for-byte afterwards.
The whole sequence is **re-derivable**: `experiments/exact_memo/run_plants.py`

|---|---:|

The sharpest red is the sixth: with `kill_fraction` scaled, the suite reported

## 9. Reproduce

```sh
export TMESIM_STATE_DIR=experiments/surrogate_feasibility/_state
./.venv/bin/python experiments/exact_memo/axis_exponents.py      # from the 2026-10-09 sweep
./.venv/bin/python experiments/exact_memo/probe_scaling.py 30 3600   # 35 real solves
./.venv/bin/python experiments/exact_memo/summarise_probe.py
./.venv/bin/python experiments/exact_memo/measure_speedup.py xenium_breast 30 21600
./.venv/bin/python experiments/exact_memo/verify_against_solve.py
# the shipped resolution, ~5 min of solves:
./.venv/bin/python experiments/exact_memo/measure_speedup.py xenium_breast 12 21600
./.venv/bin/python -m pytest tests/test_memo.py
./.venv/bin/python experiments/exact_memo/run_plants.py          # sec. 8, ~2 min
./.venv/bin/python experiments/exact_memo/check_report.py \
    results/exact_memo_2026-10-10.md
```

`_state` holds the ingested-section registry (shared with the 2026-10-09
study) so the ingested sections resolve; the built-in sections need
`data_cache/` populated as `vivum sections` describes. `tests/test_memo.py`
picks the first cached section it finds and SKIPS itself when none is cached,
so it does not pin a specimen and nothing it asserts is a property of one.

`check_report.py` re-verifies this file the way
`experiments/surrogate_feasibility/check_report.py` verifies yesterday's: no
placeholder survives, and every decimal of 4 or more significant digits appears
verbatim in one of this study's data files or in a repository source it cites.
The full planted-defect log, including the red output quoted in §8, is
`experiments/exact_memo/plants.json`.

The route is mounted with ONE line inside `create_app` in `app/server/api.py`,
immediately after the workspace router and **before** `_mount_web(app)`:

```python
    app.include_router(build_memo_router(jobs=jobs))
```

`build_memo_router` joins the lazy import block that already holds
`build_browse_router` and `build_workspace_router` two lines above it — the
house pattern, because `fastapi` is in the optional `[app]` extra and
`api.py` imports every router from inside `create_app`. Verified end to end
against a real `TestClient` with the line temporarily in place: a miss before
the spec is solved, `exact_memo` on the same spec afterwards,
`algebraic_scale` with `bit_exact: true` at a 4x dose, and a miss for a window
change. `api.py` was then restored byte-identical and is NOT edited by this
change.

`tests/test_memo.py::TestRoute` asserts both halves of that placement — that
the route answers when registered ahead of the web mount, and that it is never
reached when appended after it.

**The claim this file makes, in one sentence:** a spec already solved can be
answered at zero error and a spec differing only in dose or half-life can be
answered by an exact identity — provided the key covers the engine as well as
the spec, and provided "exact" is read as *exact in exact arithmetic*, which
for the dose axis is bit-exact only when the ratio is a power of two.
